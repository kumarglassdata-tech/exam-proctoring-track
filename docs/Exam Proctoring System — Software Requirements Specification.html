1. Introduction

1.1 Purpose

This document specifies the functional and non-functional requirements, system architecture, technology stack, AI models, API contract, and data model for the Interview & Exam Proctoring System — a Windows desktop exam client with real-time anti-cheat detection, a backend service layer, and a web dashboard for the proctor/incharge to observe and manage live exams.

1.2 Scope

The system lets an organization run remote exams/interviews where:

  • A candidate installs and runs a locked-down Windows .exe client to take the exam.
  • The client detects and reports cheating signals (webcam, screen, audio, app/process activity) in real time.
  • A proctor/incharge watches live candidates and post-exam recordings from a web dashboard, and can intervene.
  • A backend orchestrates sessions, stores data, runs heavier analytics, and generates reports.

Out of scope for v1: Android/mobile client, browser-only (non-installed) exam mode, and non-Windows operating systems.

1.3 Definitions & Acronyms

Term Meaning
Candidate The person taking the exam
Incharge / Proctor The person monitoring exams from the admin dashboard
SFU Selective Forwarding Unit — WebRTC media relay server
Flag A recorded anti-cheat event/anomaly
Integrity Score Aggregate risk score computed from all flags for a session
JIT Just-in-time (question delivery, decrypted only when needed)

1.4 Intended Audience

Developer(s) building and maintaining the system; this doc is the single reference for what to build, in what stack, and how the pieces talk to each other.

2. Overall Description

2.1 Product Perspective

Three cooperating components:

  1. Candidate App — native Windows .exe, runs on the candidate's machine, enforces lockdown and captures/analyzes media locally.
  2. Backend — FastAPI services + workers + datastores, the source of truth for sessions, questions, flags, and reports.
  3. Admin/Incharge Dashboard — Next.js web app for proctors and admins to watch, intervene, and review.

2.2 User Classes

User Class Description Primary Interface
Candidate Takes the exam under monitoring Windows .exe
Proctor / Incharge Watches live exams, can pause/terminate/chat Web dashboard
Admin Manages question banks, users, retention policy, reports Web dashboard
System Automated analytics/report generation Backend workers

2.3 Operating Environment

  • Candidate side: Windows 10/11, x64, webcam + microphone required, broadband internet.
  • Server side: Linux containers (Docker), cloud or on-prem hosting.
  • Admin dashboard: any modern browser (Chrome/Edge/Firefox).

2.4 Design & Implementation Constraints

  • Candidate client must be a single distributable, code-signed .exe (no Android/mobile build).
  • All media and flag data in transit must be encrypted (TLS/SRTP).
  • Must support India's DPDP Act consent and data-handling requirements.

2.5 Assumptions & Dependencies

  • Candidates have a Windows machine with an internal or external webcam and mic meeting minimum resolution/quality.
  • A third-party WebRTC SFU (self-hosted LiveKit/mediasoup, or a hosted provider like Agora) is available.
  • Reliable internet at the candidate's location; the client degrades gracefully (local buffering) on brief drops.

4. AI / ML Models

Task Model / Approach Library Runs Where
Face match (identity verification) ArcFace / FaceNet embeddings + cosine similarity ONNX Runtime Local (client)
Liveness detection Anti-spoofing model or blink/head-turn challenge-response ONNX Runtime Local (client)
Face-presence & multi-face detection Lightweight face detector (RetinaFace-mobile / MediaPipe Face Detection) ONNX Runtime / MediaPipe Local (client)
Gaze / eye tracking MediaPipe Iris or a similar landmark-based gaze model MediaPipe / ONNX Local (client)
Object detection (phone, book, second person, earphones) YOLOv8n (nano variant, for low latency) ONNX Runtime Local (client)
Keystroke-dynamics anomaly Statistical/ML classifier trained on the candidate's own typing baseline scikit-learn Server-side (batch)
Mouse-movement anomaly Isolation Forest or autoencoder on movement features scikit-learn / PyTorch Server-side (batch)
Answer similarity / plagiarism Sentence embeddings + cosine-similarity clustering sentence-transformers Server-side (Analytics Workers)
Aggregate risk scoring Weighted rule-based score initially, evolving to a trained classifier XGBoost / LightGBM Server-side (Analytics Workers)

Design note: anything that needs to flag within the exam session (face, gaze, objects) runs locally in the client for low latency and to keep bandwidth down — only the flag event, not raw video, needs to reach the backend in real time. Anything that benefits from looking across many candidates or the full recording (plagiarism, risk scoring, keystroke baselines) runs server-side, asynchronously.

5. Functional Requirements

5.1 Identity & Access Verification

  • FR-1.1 The system shall capture a live selfie and match it against the candidate's registered profile photo before allowing exam entry.
  • FR-1.2 The system shall re-verify the candidate's identity at random intervals during the exam, no less frequently than every 10 minutes.
  • FR-1.3 The system shall perform liveness detection to reject a static photo or replayed video as the camera input.
  • FR-1.4 The system shall require two-factor authentication before unlocking the exam.
  • FR-1.5 The system shall reject a login attempt for an account with an already-active session elsewhere.
  • FR-1.6 The system shall bind a session to a single device fingerprint for its duration.

5.2 Webcam Monitoring

  • FR-2.1 The system shall record continuous webcam video for the full session duration.
  • FR-2.2 The system shall flag when no face is detected in frame for longer than a configurable threshold.
  • FR-2.3 The system shall flag when more than one face is detected in frame.
  • FR-2.4 The system shall flag sustained gaze away from the screen.
  • FR-2.5 The system shall flag detected prohibited objects (phone, book, second screen, earphones) in frame.
  • FR-2.6 The system shall capture randomized snapshots independent of continuous recording, for audit purposes.

5.3 Screen Monitoring

  • FR-3.1 The system shall record the full screen for the session duration.
  • FR-3.2 The system shall stream the screen live to the proctor dashboard.
  • FR-3.3 The system shall detect and flag additional connected monitors.
  • FR-3.4 The system shall detect and flag known remote-access/mirroring software running on the machine.
  • FR-3.5 The system shall detect indicators of the client running inside a virtual machine or sandbox.

5.4 App & Device Lockdown

  • FR-4.1 The system shall enforce full-screen kiosk mode for the duration of the exam.
  • FR-4.2 The system shall intercept and block window/task switching.
  • FR-4.3 The system shall block copy/paste into and out of the exam window.
  • FR-4.4 The system shall block prohibited keyboard shortcuts (Windows key, Print Screen, etc.).
  • FR-4.5 The system shall detect and flag/close disallowed background applications per a configurable block-list.
  • FR-4.6 The system shall prevent more than one instance of the client, or more than one active exam session, from running simultaneously.
  • FR-4.7 The system shall suppress OS notifications for the session duration.

5.5 Audio Monitoring

  • FR-5.1 The system shall record continuous microphone audio for the session duration.
  • FR-5.2 The system shall flag detection of a second voice.
  • FR-5.3 The system shall flag anomalous background noise patterns.

5.6 Network & Session Security

  • FR-6.1 The system shall log the candidate's IP address and flag access from outside an approved region, if geofencing is configured.
  • FR-6.2 The system shall detect and block known VPN/proxy usage.
  • FR-6.3 The system shall buffer session data locally and resume upload automatically after a network interruption, without data loss.

5.7 Behavioral Analytics & Risk Scoring

  • FR-7.1 The system shall log every window-focus loss with its duration.
  • FR-7.2 The system shall log every blocked copy/paste attempt.
  • FR-7.3 The system shall compute an aggregate integrity/risk score per session from all recorded signals.
  • FR-7.4 The system shall detect unusually high similarity between candidates' answers.

5.8 Exam Content Security

  • FR-8.1 The system shall randomize question order and answer-option order per candidate.
  • FR-8.2 The system shall deliver questions just-in-time and encrypted, never bundling the full set client-side.
  • FR-8.3 The system shall prevent screenshot capture of the exam window at the OS level where supported.
  • FR-8.4 The system shall disable printing during the exam.

5.9 Live Proctoring

  • FR-9.1 The system shall provide a live grid view of all active candidates to the proctor.
  • FR-9.2 The system shall push real-time flag alerts to the proctor dashboard.
  • FR-9.3 The system shall allow a proctor to message a candidate during the exam.
  • FR-9.4 The system shall allow a proctor to pause, resume, or terminate a candidate's session remotely.

5.10 Pre-Exam Setup

  • FR-10.1 The system shall run a system compatibility and bandwidth check before allowing exam start.
  • FR-10.2 The system shall present a "clear desk" checklist the candidate must actively confirm.
  • FR-10.3 The system shall capture explicit recording consent before any capture begins.

5.11 Post-Exam Reporting

  • FR-11.1 The system shall generate a timestamped timeline of all flagged events per session.
  • FR-11.2 The system shall produce a downloadable PDF/CSV report per session.
  • FR-11.3 The system shall support exporting a full evidence package (recordings + logs) for a session.

8. External Interface Requirements

8.1 User Interfaces

  • Candidate client: pre-exam wizard, exam screen, timer, submission screen.
  • Admin dashboard: live grid, candidate focus view, alerts panel, reports, admin console.

8.2 Hardware Interfaces

  • Webcam (minimum 720p recommended), microphone, and a display, all on the candidate's machine.

8.3 Software Interfaces

  • WebRTC SFU (LiveKit / mediasoup / Agora) for live media relay.
  • ONNX Runtime for local model inference.
  • Object storage API (S3-compatible) for recordings and evidence.

8.4 Communication Interfaces

  • REST over HTTPS (TLS 1.3) for CRUD operations.
  • WebSocket (WSS) for real-time flags and chat.
  • WebRTC (SRTP) for live audio/video/screen streams.

9. Non-Functional Requirements

ID Category Requirement
NFR-1 Performance Local AI detection (face/gaze/object) shall complete within ~300ms per sampled frame on typical candidate hardware.
NFR-2 Performance A real-time flag shall reach the admin dashboard within 2 seconds of detection.
NFR-3 Security All network communication shall use TLS 1.3.
NFR-4 Security Recordings and evidence shall be encrypted at rest (AES-256).
NFR-5 Security JWTs shall expire within a short configurable window with refresh-token rotation.
NFR-6 Reliability The client shall buffer locally through short network interruptions without data loss.
NFR-7 Availability Backend services shall target 99.5% uptime during scheduled exam windows.
NFR-8 Scalability The WebRTC SFU tier shall scale independently of the API tier.
NFR-9 Usability Pre-exam checks shall complete in under 5 minutes on a standard broadband connection.
NFR-10 Compliance Explicit recording consent shall be captured before capture begins, per India's DPDP Act (and GDPR where applicable).
NFR-11 Compliance Data retention periods shall be configurable per exam/organization.
NFR-12 Maintainability The client-backend API contract shall be versioned so either side can be updated independently.

10. Appendix — Glossary

Term Meaning
